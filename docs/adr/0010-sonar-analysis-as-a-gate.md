# Sonar analysis as a gate

Every pull request and every push to `main` carries a SonarQube Cloud analysis of `Domingax/oryndra`: its quality gate, its new issues, its duplications and the coverage of the movement core. It runs in a second job of `.github/workflows/verify.yml` — `sonar`, beside `verify` — wrapping the SonarScanner for .NET around a build and the core tests, with the token in the `SONAR_TOKEN` repository secret and the scope of the analysis in `SonarQube.Analysis.xml`.

The gate **binds**. The job waits for it and fails with it (`sonar.qualitygate.wait`), and the `Sonar gate` ruleset on the default branch requires a pull request carrying the `SonarCloud Code Analysis` check that the SonarQube Cloud app posts: a failed gate leaves a pull request that cannot be merged, and a passing one shows the gate, the new issues and a link to the analysis on the pull request itself. `./verify.sh` keeps its own job and stays what it always was — the command that decides locally, unchanged, offline, with no token.

## Considered and rejected

- **A report that binds nothing** (what this ticket first asked for): a summary nobody is held to is read once. The owner made the separate decision the ticket anticipated — turn it into a gate — before this change landed, so the enforcement is here rather than in a follow-up. What it costs is written down below, under consequences.
- **A self-hosted SonarQube**: hosting, upgrading, backing up and securing a server for one public repository. SonarQube Cloud is free for public code, and it is already what the agents' SonarQube tooling in this environment points at, so a second instance would be a second truth.
- **Automatic analysis** (SonarQube Cloud can analyse a .NET repository with no CI at all): no coverage — which is half of what this analysis is for — no analysis of non-default branches, no readable logs, and it refuses to coexist with a CI-based analysis, so that toggle has to be off (see the consequences).
- **Folding the scanner into `./verify.sh`**: the scanner rewrites the build's ruleset and turns warnings-as-errors off, so the gate would stop being the command that is trusted exactly while it runs; and it needs a token, so the local loop would stop working without one. A second command, and a second job, keeps the gate one command that works on a machine that has never heard of Sonar.
- **Coverage of the whole solution**: nothing in this repository records line coverage for the Godot layer, which is proven by booting the project and by the runtime tests. Counting it would report a percentage nobody can move and hide the one that matters, so `sonar.coverage.exclusions` narrows coverage to `src/Oryndra.Core` (see `docs/testing.md`).
- **`sonar-project.properties`** (the obvious file to reach for, and the one this ticket asked for): the SonarScanner for .NET does **not** read it. It is the CLI scanner's convention; the .NET scanner reads its own `SonarQube.Analysis.xml`, passed with `/s:`, and its log says so (`sonar-project.properties files are not understood by the SonarScanner for MSBuild`). A file that looks authoritative and changes nothing is worse than no file, so the scope lives in the file this scanner actually reads.
- **Excluding the test projects from the analysis** (`sonar.dotnet.excludeTestProjects`): tests are analysed as test code, which is what lets Sonar tell a test from a source file instead of asking for tests of tests.

## Consequences

- CI has two jobs. `verify` is the build gate: the same `./verify.sh` as always. `sonar` is the analysis gate: it builds, runs the core tests for coverage, uploads the analysis, and waits for the verdict. Only the default branch and pull requests are analysed, because the free plan offers no branch analysis, and a pull request from a fork is skipped rather than failed, because it carries no secret. The two jobs repeat three steps — the checkout, the SDK, the NuGet cache — rather than sharing a composite action: for two jobs, three duplicated `uses:` lines are cheaper to read than an indirection to follow, and a version bump is a two-line change.
- **`main` takes changes through pull requests.** The `Sonar gate` ruleset on the default branch requires a pull request and the `SonarCloud Code Analysis` check, so a red or absent gate leaves nothing to merge; it asks for zero approvals, which is what keeps a solo workflow moving. A pull request from a fork cannot be merged at all: no secret, no analysis, no check. If that check ever has to be satisfied without an analysis — the SonarQube Cloud app down, say — the escape hatch is the ruleset, and its settings live in the repository, not in this file.
- **What the gate checks lives in the SonarQube Cloud UI**, outside this repository: its conditions and thresholds are a setting no commit records, and changing them changes what can be merged. That is the price of binding, and it is why the gate's verdict is read back on the pull request rather than inferred from the build.
- The `sonar` job builds with warnings *not* treated as errors: the Sonar rules arrive as build warnings, and a job that fails on them would fail on findings the gate has not judged yet.
- `SonarQube.Analysis.xml` at the repository root carries what is analysed, what is measured, what is excluded, and the wait for the gate. The project key, the organization and the token are not in it: the key and the organization belong to the CI step, the token to the repository secret.
- Coverage, as reported, means `src/Oryndra.Core`. A change to the movement rules moves it; a change to the Godot layer does not, and is proven at the boot and runtime levels instead.
- The pull request decoration — the comment carrying the gate, the new issues and the link — is SonarQube Cloud's own, posted through the GitHub app that reads the repository, not by the `sonar` job. It only appears for a project *bound* to its repository, so a missing comment is a question for that binding, not for the job.
- The SonarQube Cloud project must not have *automatic analysis* enabled (project → Administration → Analysis Method): SonarQube Cloud documents that a CI-based analysis fails while both are on. A red `sonar` job is worth reading before assuming the code is at fault.
- How to read a report — the pull request, and the tools an agent uses — is in `docs/testing.md`.

## Evidence

Issue #17, which asked for a report and reserved the decision to make it bind; the owner took that decision in the same ticket, before the change landed. Then the `sonar` job, `SonarQube.Analysis.xml`, the ruleset on `main`, and the SonarQube Cloud documentation: *SonarScanner for .NET* (begin / build / end, `sonar.token`, `/s:`), *.NET test coverage* (`sonar.cs.cobertura.reportsPaths`), *Configuring GitHub project binding* (the decoration, and requiring the `SonarCloud Code Analysis` check), *Automatic analysis* (its limits, and the conflict with a CI analysis). For `sonar-project.properties`: the scanner's own log line and the Sonar community's answer, *"You cannot define properties in a sonar-project.properties file"* when using the SonarScanner for .NET. `docs/testing.md` states what this report does **not** replace.
