# Godot MCP as the agents' eyes on a running game

An agent working in this repository can inspect a **running** oryndra: the live scene tree, the debug output, a screenshot, and simulated input. That arrives through one MCP server — **Godot MCP Runtime** (`godot-mcp-runtime`, MIT, by Erodenn) — pinned at release **3.8.1** and started from `opencode.json` through `scripts/godot-mcp.sh`, which resolves the same `godot-mono` binary `./verify.sh` uses.

This is **observability only**. `./verify.sh` stays the authority that decides whether a change is acceptable, no test and no CI job starts this server, and a broken, absent or slow MCP server never makes a change wrong. What it buys is the one thing the headless gate cannot give: the ability to look at the game instead of reasoning about it from source.

## Considered and rejected

Candidates were compared on four axes the ticket names — capabilities (does it see a **running game**, or only files and the editor?), install footprint (what it adds to this repository), maintenance and trust (who runs it, what it talks to, where the code goes), and C# / .NET compatibility (the game is C# on Godot 4.7.2 mono, ADR-0002 and ADR-0009).

| Server | Running game | Footprint | Licence / trust | State |
|---|---|---|---|---|
| **Godot MCP Runtime** (chosen) | Yes: screenshots, input, live scene tree, debug output | **None**: transient autoload, `project.godot` restored | MIT, local process, no account | 3.8.1, active |
| Coding-Solo/godot-mcp | No: launches the editor, runs the project, reads its debug output — no screenshot, no live tree | None (`npx`) | MIT, local | 6.1k stars, last release 0.1.1, last push 2026-04 |
| IvanMurzak/Godot-MCP | Editor-side tools; runtime error capture is opt-in | **Committed C# addon** + three `PackageReference`s + an `EmbeddedResource` in the game `.csproj` | Apache-2.0, but the required RQL package is PolyForm Shield (see below); cloud backend by default | 291 stars, very active |
| hi-godot/godot-ai | Editor-live only; C# is text-only | Committed addon + a Python server through `uv` | MIT; opt-out telemetry | 3k stars, very active |
| satelliteoflove/godot-mcp | Yes, with a frozen clock and JSON state digests | Committed editor addon, plus a second server for the game console | MIT, local | 178 stars, active |
| bradypp/godot-mcp | No: file-level | None | MIT | Stale since 2025-05 |

- **Coding-Solo/godot-mcp** is the most popular and the one this server was built on, but it cannot answer the ticket's own bar: it has no screenshot and no running scene tree, so the minimum "read the running scene tree, read the error log, capture a screenshot" fails on two of three. Its runtime half is also the least maintained of the field.
- **IvanMurzak/Godot-MCP** is the C#-native option and tempting in a C# project, but paying for it touches the game itself: the addon is committed under `game/`, three NuGet packages and an `<EmbeddedResource>` go into `Oryndra.Game.csproj`, and Godot compiles everything under the project into one assembly — so a tool for looking at the game becomes a dependency of the game's build. Its editor tool layer is data-driven by `com.IvanMurzak.Rql`, **PolyForm Shield**, a source-available licence that GPL-3.0 code (ADR-0004) cannot depend on. And by default the agent's eyes go through a third-party cloud (`ai-game.dev`) behind an OAuth login: an account, a round trip, and an offline mode to reason about, for a capability that exists entirely on this machine.
- **hi-godot/godot-ai** has the largest following of the addon-based servers, but it drives the **editor**, not the game, and it documents C# as text-only — the one thing this project's scripts are. It also wants an addon committed and a `uv`-managed Python server.
- **satelliteoflove/godot-mcp** has the most interesting runtime model (freeze and step the game clock, read state as JSON rather than pixels) and is a fair second choice. It loses on footprint — a committed editor addon, plus a companion server for the console — and on fit: deterministic stepping is a feature for automated playtests, which this repository already does at the core level, headlessly, without an engine.
- **A committed addon at all**: refused as a class, not per server. The Godot project is deliberately minimal and the Godot level exists only for what the engine can break (`docs/testing.md`); a development tool that must live inside `game/` inverts that. A **C#** addon goes further and lands in the game itself: Godot compiles every `.cs` under the project into one assembly, its `PackageReference`s go into `Oryndra.Game.csproj`, and Sonar analyses it — the tool becomes a dependency of the game. A **GDScript** addon stays out of the assembly, but it still sits in this repository, is listed in `project.godot`, loads every time the project opens, and is owned by whoever maintains it rather than by us. Neither is refused for ever: it would take a new decision, made for the capability that needs it, not a bump of this one.
- **No MCP server** (keep copying logs by hand): the honest default, and rejected because the ticket exists to remove exactly that hand-off. An agent that can run the game and look at it stops asking a human to paste a screenshot back.
- **Summer Engine and the paid editor servers** (Godot MCP Pro, GDAI): a non-stock engine with a sign-in, or a proprietary addon, for the same three capabilities the pinned `npx` server gives against stock Godot. They were not evaluated further than that.

## Consequences

- **The footprint in this repository is three files beyond the documentation**: `opencode.json` (the server entry), `scripts/godot-mcp.sh` (resolves `godot-mono` — the server's own auto-detection looks for `godot` and finds nothing on a machine whose .NET Godot is named `godot-mono` — and pins 3.8.1), and `game/.gitignore` (the runtime's artifact directory; the server writes that file itself when it is missing). The server installs **no addon**: it injects a temporary autoload into the running game and removes it on stop, restoring `project.godot` — checked after a run, which left `game/project.godot` untouched.
- **Nothing in the gate changes.** `./verify.sh` does not start the server and does not know it exists; CI never installs it. The `sonar` job never sees it. The pin lives in `scripts/godot-mcp.sh` and `docs/toolchain.md`, where it is a documented version to bump, not a build input.
- **The artifacts of a run stay out of version control**: the bridge's scripts, policies and screenshots land in `game/.mcp/`, which `game/.gitignore` ignores. The server writes that `.gitignore` itself when it is missing; committing it means a run leaves the tree clean either way.
- **Starting a game is the human's call.** The server asks for confirmation through MCP elicitation before it launches a project (`run_project`), which OpenCode renders as a form; unattended runs have to answer it, or be pointed at an already-running game (`attach_project` — which costs the captured debug stream, since only a game the server spawned has one). That prompt is the reason to keep the server's security gate on rather than hand it the flags that disable it.
- **Screenshots need a display; the gate does not.** Observing a game runs a window (off-screen in background mode) and captures a real viewport. `./verify.sh` keeps booting Godot headlessly and stays valid on a machine with no display and no MCP server.
- **The tools are the server's, not ours.** Its 39 tools include scene and script editing, which duplicate what an agent does with files and `dotnet`; only the runtime half — scene tree, debug output, screenshot, input — is used here, and the operating notes say so (`docs/agents/godot-mcp.md`).
- **A screenshot is evidence for a human, never a test.** The repository has no golden images and does not gain any: feel is judged by a person playing, and pixels are what an agent looks at while iterating. Nothing here changes `docs/testing.md`'s levels; the document gains a line saying so.

## Evidence

Issue #3, whose bar was the survey, the chosen server, the wiring, three capabilities, and the explicit statement that the gate remains the authority. Candidate facts come from each project's own README, GitHub API metadata and npm registry, read on 2026-10-17 — stars, last push, licence, install shape, and C# support are as each project states them, and Godot MCP Runtime's own comparison page (`docs/comparison.md`) was used as a lead, not as a source. The licence concern for IvanMurzak/Godot-MCP is its README's own statement about `com.IvanMurzak.Rql` (PolyForm Shield) against ADR-0004 (GPL-3.0 code).

The choice was then exercised end to end, on this machine, against `game/`: `check_project` reported Godot `4.7.2.stable.mono`; `run_project` brought the project up with the bridge; `get_debug_output` returned the boot line `oryndra: simulation running`; a `run_script` read the live tree (`/root/Main`, script `res://Scripts/Main.cs`, its `Ticks` advancing); `simulate_input` delivered a key; `take_screenshot` wrote a 1152×648 PNG under `game/.mcp/`; `stop_project` cleaned up and left the working tree clean.

The other half — an agent with hands in the **editor**, not just eyes on the game — was studied afterwards, by running the two editor-driving candidates for real and measuring what each one costs: `docs/research/godot-editor-mcp-servers.md`. That study is a trace, not a decision: it wires nothing, and this ADR stands as the choice for the running game.
